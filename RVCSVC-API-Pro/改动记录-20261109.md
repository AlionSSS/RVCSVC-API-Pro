## 2. 改动一：模型常驻（`app_rvc.py`）

### 问题

7897 侧的 `/run/infer_change_voice` 每次调用都会重新读取 `.pth` 权重与 index 文件。连续翻唱同一音色时（日常只有 `Klee_Nahida_Mix_X.pth` 一个模型），这部分完全是无谓开销，实测每次 0.5–8 秒（取决于 index 大小与磁盘缓存）。

### 做法

`switch_model()` 记忆 7897 当前已加载的模型名，同名且 index 已就绪时直接返回，不再发请求。

```python
_LOADED_MODEL = None
_LAST_SWITCH_SKIPPED = False

def switch_model(model_name, force=False):
    global _LOADED_MODEL, _LAST_SWITCH_SKIPPED
    if not model_name or model_name == "无可用模型":
        return "❌ 请先选择一个有效的模型"
    if not force and _LOADED_MODEL == model_name and current_model_index:
        _LAST_SWITCH_SKIPPED = True
        print(f"[模型] {model_name} 已常驻 7897，跳过重复加载")
        return f"✅ 当前已是模型: {model_name}"
    msg = change_model(model_name)
    _LAST_SWITCH_SKIPPED = False
    _LOADED_MODEL = model_name if str(msg).startswith("✅") else None
    return msg
```

配套两点：

1. **失败自愈**：`_run_single_track_infer` 中，若本次走了「跳过」却推理失败（例如 7897 中途重启），清空 `_LOADED_MODEL` 强制重新加载并重试一次。
2. **按钮语义**：「切换模型」按钮改为 `switch_model(m, force=True)`，手动点击一律重载，用于在 RVC WebUI 里手动换过模型后重新对齐。

### 实测

| 操作                           | 耗时         | 结果                   |
| ---------------------------- | ---------- | -------------------- |
| 首次切到 `Klee_Nahida_Mix_X.pth` | 0.50s      | 加载成功，index 自动匹配      |
| 再次切同名                        | **0.000s** | 跳过，日志「已常驻 7897」      |
| 传空模型名                        | —          | `❌ 请先选择一个有效的模型`，不发请求 |
| 点「切换模型」（force）               | 0.45s      | 强制重载成功               |

## 3. 改动二：UVR 重建重采样换 `soxr_hq`（主要提速来源）

### 定位过程

对 `AudioPre._path_audio_` 做 cProfile（225.3s 的歌，总耗时 25.9s）：

| 部分                                            | 耗时    | 占比  |
| --------------------------------------------- | ----- | --- |
| `cmb_spectrogram_to_wave`（重建波形，含 2 次调用：人声+伴奏） | 15.6s | 60% |
| ├─ `res_type="scipy"` 的 FFT 重采样               | 11.5s | 44% |
| GPU 模型推理 `_execute`                           | 5.5s  | 21% |
| ISTFT（`librosa.istft`）                        | 2.8s  | 11% |

结论：**瓶颈在 CPU 侧重采样，不在 GPU**。`scipy` 重采样会对整段 14700 Hz → 44100 Hz 的音频做全局 FFT，代价随长度线性增长。

### 修改

`uvr5/lib/lib_v5/spec_utils.py`：

- 第 411 行：`res_type="sinc_fastest"` → `res_type="soxr_hq"`
- 第 427 行：`res_type="scipy"` → `res_type="soxr_hq"`


### 实测（6 首不同歌曲，每首预热后跑 2 次取中位数）

基线 = 文件 `spec_utils.py` 的原始设置（`sinc_fastest` + `scipy`），改后 = `soxr_hq`；两者仅差这两个参数，其余代码、模型、输入完全一致。

| 歌曲 | 时长 | 采样率 | 改前 | 改后 | 提速 |
| --- | --- | --- | --- | --- | --- |
| 杨丞琳 - 雨爱 | 4.34 min | 44.1k | 37.41s | **14.12s** | **2.65×** |
| G.E.M.邓紫棋 - 自由的你 | 4.95 min | 48k | 30.22s | **20.83s** | 1.45× |
| 梁静茹 - 勇气 | 3.99 min | 44.1k | 20.53s | **13.13s** | 1.56× |
| 梁心颐 - 下雨天 | 4.22 min | 44.1k | 19.85s | **13.92s** | 1.43× |
| Kalafina - 五月雨が過ぎた頃に | 4.36 min | 44.1k | 18.79s | **14.47s** | 1.30× |
| 梁静茹 - 夜夜夜夜 Live | 4.52 min | 44.1k | 18.09s | **14.97s** | 1.21× |
| **平均** | — | — | **24.15s** | **15.24s** | **1.58×** |

- 6 首全部提速，没有一首变慢；单曲提速中位数 1.44 倍，平均每首省 8.9 秒。
- `自由的你` 改前改后都偏慢，因为它是 48kHz 源（多一道 48k→14.7k 的重采样），属输入差异，与本次改动无关。

### 音质差异（6 首 × 人声/伴奏 = 12 轨）

| 指标 | 结果 |
| --- | --- |
| SI-SDR（以改前为参考） | **96.6 – 106.1 dB**（人声轨 101.3–104.2 dB） |
| 最大样本偏差 | **3.05e-05**，正好等于 1 个 16bit LSB |
| 差异分布 | 中位差 **0**；99.99% 样本差 ≤1 LSB |
| 对数谱距离 LSD（均值 / P95） | 0.00–0.01 dB / 0.02–0.07 dB |
| 14–20 kHz 高频能量差 | **±0.00 dB**（重采样滤波器差异未在高频留下可测偏差） |

唯一例外：`夜夜夜夜 Live` 的伴奏轨有 128 帧（占 0.0011%）超过 1.5 LSB，最大 5.71e-03，位置集中在 **0.0s 与 270.9s**——即文件首尾边界，两种重采样器在边界处的补零/卷绕处理不同所致，中段完全一致。输出为 16bit PCM，差异本质上就是 ±1 个量化步长的舍入，不可听。

### 补充：零差测试（逐样本统计）

为了把「差异到底有多小」量化到样本级，另取 `勇气`、`雨爱` 各截一段 60s（中段，含完整主唱与伴奏），同一输入分别跑基线与 `soxr_hq`，统计 16bit 落盘后的逐样本差异：

| 片段 / 轨 | 逐位完全相同 | ≤1 LSB | 去掉首尾 10ms 的 SI-SDR | 误差 RMS | 中段最大偏差 |
| --- | --- | --- | --- | --- | --- |
| 勇气 / 人声 | 99.24% | 99.94% | **90.7 dB** | −110.8 dBFS | 5 LSB |
| 勇气 / 伴奏 | 99.77% | 99.99% | **100.0 dB** | −117.2 dBFS | 1 LSB |
| 雨爱 / 人声 | 99.75% | 99.98% | **100.2 dB** | −116.7 dBFS | 2 LSB |
| 雨爱 / 伴奏 | 98.65% | 99.85% | **93.3 dB** | −105.4 dBFS | 14 LSB |

关键结论：

- 稳态误差 **−105 ~ −117 dBFS**，低于 16bit 容器自身的量化噪声底（约 −101 dBFS）——也就是说，这个差异在 16bit 输出里已经**小于一个量化步长**，无法被格式本身表达。
- 误差谱平坦度 0.84、与信号相关系数 ≈0.00，即差异是**白噪声型舍入残差**，没有结构化残留（不是「少了高频」「多了齿音」这类可辨特征）。配合 LSD ≤0.07 dB、14–20 kHz 能量差 ±0.00 dB，可确认音色/频响未被改动。
- 整段 SI-SDR 只有 66–85 dB，是被**首尾各 1–2 个样本**拉低的：那些点的偏差可达数百至数千 LSB（本次硬切片段起始电平高达 0.44 FS，反差最大），但只持续 0.02–0.05 ms，且位于文件第一个/最后一个样本处。真实歌曲首尾通常是静音或淡入淡出，此处差分接近 0。

### 为什么 `雨爱` 提速 2.65 倍（scipy 的隐藏坑）

`scipy` 走的是 FFT 重采样，开销取决于数组长度的**最大质因数**（大质数会退化成 Bluestein 算法）。逐次记录 14700→44100 那次调用：

| 歌曲 | 输入样本数 | 最大质因数 | 该次重采样耗时 | 整段分离 |
| --- | --- | --- | --- | --- |
| 五月雨 | 3,845,440 | 197 | 3.62s | 18.8s |
| 雨爱 | 3,828,960 | **2659** | **21.63s** | 37.4s |

样本数只差 0.4%，耗时差 **6 倍**。也就是说改前的分离耗时**逐曲不可预测**（18–37s 之间跳），而 `soxr_hq` 与长度/内容无关，稳定在 13–15s。`自由的你` 改后仍 20.8s，也是同一原因（48k 输入多一道重采样，绝对值整体上移）。

> 补充：第 3 节开头那次 cProfile（总 25.9s、scipy 占 11.5s）是**首次运行的冷启动**数据，绝对值偏高；预热后基线为 18–20s，本节表格是预热后的复测值，以本节为准。

### 附一：三项「零成本」优化的实测（已否决）

297s 干声、`Klee_Nahida_Mix_X`、`rmvpe`、`index_rate=0.75`、RTX 2070S 8G 独占、三轮中位数：

| 方案 | 总耗时 | 相对现状 | 结论 |
| --- | --- | --- | --- |
| 现状（`x_center=60`，faiss 用 numpy） | 9.73–9.86s | 基准 | — |
| faiss 8 邻居加权挪 GPU（fp32 向量表） | 9.57–9.63s | **−0.19 ~ −0.27s** | 唯一正收益，但只有原估的 1/3 |
| 16k 干声缓存（npy 复用，省重复解码） | — | **≈0** | `load_audio` 只花 36ms，无油水 |
| `x_center` 60→100（5 段→3 段） | 10.65–11.60s | **+0.81 ~ +1.74s** | 负收益 |
| `x_center` 60→40（5 段→8 段） | 9.63–9.88s | ±0 | 持平 |

**现状耗时拆解**（同上条件，中位数）：

| 环节 | 耗时 | 说明 |
| --- | --- | --- |
| `net_g` 合成（5 段） | 4.95s | 唯一大头，只有 TRT 能动 |
| `change_rms` 音量包络对齐 | 0.79s | 全 GPU 可降到 51ms |
| RMVPE 提 F0 | 1.00s | |
| faiss `read_index` + `reconstruct_n` | 0.205s | 每首重建一次，常驻可归零 |
| faiss `search`（CPU，`nprobe=1`） | 0.159s | CPU faiss，挪不了 |
| faiss 8 邻居 gather + 加权（numpy） | 0.220s | 挪 GPU 后 0.026s |
| `load_audio`（torchaudio GPU 解码 + GPU 重采样） | 0.036s | 已无空间 |
| HuBERT 特征 | 0.080s | |
| `filtfilt` | 0.070s | |
| 分块/拼接/int16/HTTP 等 | ≈1.0s | |

**三个数字为什么和预估差这么多**

1. faiss 的 0.90s 里只有 0.22s 是 numpy 的 gather+加权，另外 0.16s 是 CPU 检索、0.21s 是每首重建索引。挪 GPU 只能干掉那 0.22s。
2. `load_audio` 早就走 torchaudio GPU 解码 + GPU 重采样，只要 36ms。之前把 3.19s 整体归给「I/O + DSP」是粗估，实际主要是 `change_rms`（0.79s）与分块拼接。
3. `x_center` 变大后单段从 60s 变 100s，`net_g` 的 conv 效率反而下降（4.95s→5.75s），抵不过省掉的那 12s 重复合成。

**音质对比方法的一个坑**：同一配置连跑两次，SI-SDR 只有 8.3 dB——`net_g` 的 fp16 卷积本身不逐位确定。所以本链路上任何基于 SI-SDR 的「改动前后音质」比较都无效，差异全在噪声底。要看等价性得看 `feats` 层：fp32 向量表的 GPU 版对 numpy 版 `max|Δ|=4.8e-7`，量化到 fp16 后仅 0.014% 元素差 1 ulp；而 fp16 向量表会让 19% 元素差 1–2 ulp。

### 附二：TensorRT / `torch.compile` 的实测依据（评估过，未实施）

**能否被 TRT 加速**：仅 `net_g` 的 4.95s（约 50%）值得动；RMVPE 1.00s 可省约 0.2s；`change_rms`、faiss 检索、I/O 都是 CPU，TRT 无关。

**关键结论**

1. **HuBERT 没有可挖空间**：297s 音频只用 0.08s（约 3700× 实时），TRT 最多再省 0.01s。
2. **只有 `net_g` 值得做**。它已是 fp16 eager（`go-webui.bat` 下 `RVC_CUDA_GRAPH` 默认 0），TRT 剩下的是 kernel 融合与卷积算法选择收益，现实倍数约 **1.2–1.4×**（不是常见的 2–3×，那个数字来自 fp32 基线）。
3. **CUDA Graph 不要开**：实测 `RVC_CUDA_GRAPH=1` 时，同一首歌首轮 **391.75s**（5 段形状各不相同，每段都要重新捕获），稳态仍有 **118s**（其中合成 108s），是 eager（9.5s）的 12 倍。`webui.py` 默认保持 eager 是正确选择，`go-webui.bat` 不要加 `RVC_OFFLINE_CUDA_GRAPH=1`。
4. **`torch.compile` 这条路本机走不通**：实测 `torch.compile(conv1d模型)` 直接抛 `TritonMissing: Cannot find a working triton installation`（torch 2.7.1+cu118、Windows、Python 3.12，官方 wheel 不带 triton）。要绕开只能装非官方 `triton-windows`，或退回 `backend="cudagraphs"`（即上面第 3 条，已实测为负）。
5. **收益换算**：`net_g` 4.95s → 3.6–4.1s，RMVPE 省约 0.2s，合计 RVC 段 9.6s → 8.2–8.7s（1.10–1.17×）；整首歌（UVR 14s + RVC 9.6s + 混音 3s ≈ 27s）折合省 1–1.6s（4–6%）。
6. **成本**：需装 TensorRT + ONNX（Windows/py312/cu118 版本匹配）、导出 `net_g` ONNX（weight_norm、Snake 激活、NSF 谐波源的 `cumsum`/`sin`、动态长度都需处理）、为不同分块长度建 optimization profile、做 fp16 数值一致性 A/B（TRT 与 torch 的 fp16 舍入不同，可能改变音色细节）、engine 绑定 GPU 架构与 TRT 版本（换驱动要重建）。

**结论**：本次不做。三项「零成本」实测合计只有 0.23s（另两项为 0 和负收益），TRT 的 1–1.6s 才是真收益；但性价比最高的仍是流水线重叠（8–10s）。


## 7. 2026-11-09 单曲流程优化实施

本次已正式实施三项单曲处理优化：

1. `RVC20260718/infer/vc/pipeline.py`：用一次累计绝对值和替代 RVC 分段点搜索中的 160 次整段扫描。默认使用新算法；设置环境变量 `RVC_SEGMENT_SEARCH=legacy` 可回退旧算法。
2. `RVCSVC-API-Pro/uvr5/vr.py`：人声和伴奏的频谱重建、重采样和写文件使用两个线程并发执行。通过 `Future.result()` 传播线程异常；设置 `UVR_RECONSTRUCTION_WORKERS=1` 可回退串行模式。
3. `RVCSVC-API-Pro/audio_cache.py`、`rvc_cache.py`、`app_rvc.py`：增加带 SHA-256、音频元数据、模型／索引／代码版本和参数校验的内容缓存。缓存采用临时文件加原子替换，并在 manifest 完整发布后才可命中。

缓存分为两层：UVR 人声／伴奏缓存和 RVC 干声缓存。混响、回声、人声音量、伴奏音量、清唱输出等后处理设置不会进入 RVC 干声缓存键，因此重复调整这些参数时可以跳过 UVR 和 RVC。改变源文件内容、模型、索引、音高算法、升降调或代码版本时会自动失效。旧的无 manifest 缓存不会被强行复用，需要首次重新生成。

验证结果：

- `py_compile` 通过：`pipeline.py`、`vr.py`、`app_rvc.py`、`audio_cache.py`、`rvc_cache.py`。
- 三首音频的 RVC 新旧分段切点完全一致。
- 当前 UVR 并发重建与改动前串行重建的六个 WAV 文件 SHA-256 完全一致。
- 缓存单元测试 5 项通过，覆盖同名文件隔离、损坏文件检测、模型／索引变化失效、缺失伴奏缓存和失败时不发布半成品。
- 真实 7897 HTTP 集成测试通过：首次转换生成缓存；只改混响时约 4.6 秒完成且跳过分离／推理；清唱复用干声；改变升降调重新执行 RVC 并复用 UVR。

单首音频的正式缓存目录位于对应 UVR 输出目录下的 `rvc_infer`，缓存文件不会在混音结束时删除。转换请求使用进程内锁串行化，以保护共享的模型和分离器状态。
